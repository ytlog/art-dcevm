01 / WHAT IT IS

把“修改代码”推进到“演进运行时”

开发 Android 应用时，我们经常面对同一种循环：修改代码、构建、安装，再重新进入刚才的页面。页面可以恢复，刚刚积累的内存状态却往往要重新准备。当问题藏在一个运行了很久的对象、一段复杂交互或一个偶发调用里，这个循环尤其昂贵。

ART DCEVM 是一个 Android 运行时类重定义增强库。它面向自有、从进程启动时就可调试的应用，在运行期间接收新的类定义，更新方法实现，并在已适配的 ART 构建上完成字段、方法以及继承关系的结构演进。项目中的 DCEVM 指向 Dynamic Code Evolution VM 的类演进方向；这里的实现落在 Android 的 ART 上。

它提供的是运行时引擎。IDE、补丁编译器和调试工具可以围绕它构建热重载工作流：工具生成新的 DEX，用户 Agent 发起重定义，ART DCEVM 负责虚拟机内的变化。应用进程继续运行，兼容的对象状态随之保留。

更新类定义，同时让运行中的对象、引用和调用保持一致。

这个目标比“把下一次方法调用切换到新代码”更深入。一个类的字段布局改变后，已有对象如何读取？被删除的方法还有旧反射引用怎么办？正在执行的机器码已经内联了旧方法怎么办？ART DCEVM 把这些问题作为同一场运行时演进来处理。

02 / WHAT IT CAN DO

方法、成员、类型关系，一起演进

最直观的能力是方法体替换：修正计算逻辑、调整调试行为，再让后续调用使用新实现。结构演进则进一步允许类的形态变化，例如新增字段、删除成员、调整签名，或者更新父类与接口关系。

变化带来的能力运行语义
方法体替换更新业务逻辑与调试代码后续调用进入新实现；活动调用按帧安全条件处理
字段、方法与构造器增删让类结构跟随代码迭代兼容字段保留值；新增字段在已有对象中为零值或 null
类型、签名与成员形态变化调整字段类型、方法签名、static / 实例或 native / Java 形式相关变化按旧成员退役、新成员建立处理
修饰符变化调整访问权限及已覆盖的 final、volatile、synchronized、abstract 语义同时检查已有子类、旧访问路径与存活实例的约束
父类与接口变化重组类型关系和分派路径同步处理接收者有效性、对象字段与已覆盖的类型缓存
批量重定义把相互依赖的类作为一次变化提交在可失败的事务边界上拒绝整批，保留旧定义

上述结构能力在已适配 Android 13 / ARM64 路径上有真机回归证据；具体组合与调用形态以 能力边界 为准。

一个对象，两个版本的类

假设运行中的 Counter 已经累加到 7。新版本保留 count，增加 label，并把 value() 改为返回 count * 2。提交完成后，这个已有对象的 count 仍为 7，新增 label 为 null，后续 value() 返回 14。

最适合怎样的工作流？

它适合开发期热重载引擎、保留会话状态的调试工具，以及研究类演进和运行时一致性的实验平台。你可以在一个已经进入复杂状态的自有应用中更改逻辑，然后继续观察结果。补丁生成、传输、校验与业务触发时机由上层工具负责，ART DCEVM 聚焦运行时执行。

验证坐标。Android 11–17 的七个 ARM64 版本已有公开 JVMTI 回归记录；Android 13 小米 CAS 的一轮完整既有演进回归通过 1,025 项检查。跨版本通用结构事务仍在接线与验收，公开路径通过不能替代完整结构能力证明。Android 12L 暂不纳入本轮验收。
03 / HOW TO USE IT

一次初始化，沿用标准 JVMTI 调用

ART DCEVM 保留工具链熟悉的入口：jvmtiEnv::RedefineClasses。应用先初始化增强库，用户自己的 JVMTI Agent 再提交新的类定义。目标类需要保持类名与加载上下文一致；Android 侧提交的是包含目标新定义的完整 DEX 字节。

第一步：构建并接入库

当前可直接从源码构建。工程使用 Gradle Wrapper 9.4.1、AGP 9.2.0、SDK 37、NDK 27.2.12479018 和 CMake 4.3.4；准备兼容 JDK，并在本机 local.properties 配置 SDK 路径。

git clone https://github.com/ytlog/art-dcevm.git
cd art-dcevm
./gradlew :app:assembleDebug :artdcevm:assembleRelease

示例 APK 位于 app/build/outputs/apk/debug/app-debug.apk，AAR 位于 artdcevm/build/outputs/aar/artdcevm-release.aar。在包含源码模块的工程中接入：

// settings.gradle 需包含 :artdcevm
// 应用模块 build.gradle
dependencies {
    implementation project(':artdcevm')
}

库的最低版本为 API 30，当前构建只支持 arm64-v8a。源码模块通过 Gradle 声明 Hook 依赖；手动接入独立 AAR 时，需要同时处理它的运行时依赖。Maven Central 发布坐标尚未上线，具体发布与依赖说明见 发布指南。

第二步：在重定义前初始化

import com.github.ytlog.artdcevm.api.DcevmRuntime;

// 在自己的 Agent 第一次发起结构重定义前调用。
// 此调用会抛出异常；由应用初始化流程处理并记录原因。
DcevmRuntime.initialize(context);

应用必须从进程启动时就处于 debuggable 状态。初始化加载增强库、附加 Agent、检查符号和运行时校准，再安装路由。成功后，同一进程的重复调用直接返回；失败时，调用方应记录诊断并停止本次结构请求。

如果工作流只需要公开 JVMTI 能力，可显式使用：

org.json.JSONObject capabilities =
        DcevmRuntime.attachPublicJvmti(context);

当前源码还提供 initializeCapabilities(context)，用于初始化并返回独立证明的能力子集。使用这个入口时应核对返回的具体范围，不把“某个子集就绪”当作“完整演进就绪”。

第三步：附加自己的 Agent

用户 Agent 在 Agent_OnAttach 中取得 JVMTI 环境并申请重定义能力。下面是最小附加示例；补丁接收、线程管理和业务接口由自己的 Agent 实现。

#include <jni.h>
#include "jvmti.h"

static jvmtiEnv* jvmti = nullptr;

extern "C" JNIEXPORT jint JNICALL
Agent_OnAttach(JavaVM* vm, char*, void*) {
    if (vm->GetEnv(reinterpret_cast<void**>(&jvmti),
                   JVMTI_VERSION_1_2) != JNI_OK) return JNI_ERR;
    jvmtiCapabilities caps{};
    caps.can_redefine_classes = 1;
    return jvmti->AddCapabilities(&caps) == JVMTI_ERROR_NONE
            ? JNI_OK : JNI_ERR;
}

编译并打包 libmy_agent.so 后，在应用中附加它。此名称代表自己的库：

android.os.Debug.attachJvmtiAgent(
        "libmy_agent.so", null, context.getClassLoader());

第四步：提交目标类与新 DEX

// target：已加载的 jclass；dex：完整的新 DEX 字节。
// 当前线程已附加到 VM；dex_size 可表示为 jint。
jvmtiClassDefinition definition{};
definition.klass = target;
definition.class_byte_count = dex_size;
definition.class_bytes = dex;

jvmtiError result = jvmti->RedefineClasses(1, &definition);
if (result != JVMTI_ERROR_NONE) {
    // 记录错误码，按原因处理；不将这次请求视为已生效。
}

多个相互依赖的类应放进同一个 jvmtiClassDefinition[] 一次提交。调用期间保持类引用和 DEX 缓冲区有效。补丁编译可参考仓库的 fixtures 与 build-fixtures.py；Agent 的完整接入参考 standard_jvmti_client.cc。代码生成本身属于上层工具链。

从示例回归开始

# 已适配 Android 13 ARM64：既有完整演进套件
python3 tools/android13/run-source-probe.py --serial DEVICE

# 其他目标设备：公开 JVMTI 回归
python3 tools/run-public-jvmti.py --serial DEVICE

脚本安装并操作示例应用 dev.artdcevm.lab，每次从初始定义启动。验证记录会关联设备、APK 哈希和当前运行报告。脚本名中的 source 沿用了历史命名；当前构建无需下载或编译 AOSP，也不加载独立源码引擎。

04 / UNDER THE HOOD

让整个运行时接受同一场变化

ART DCEVM 的关键技术，是把标准重定义请求接入 ART 的真实类事务，再协调元数据、堆对象、引用缓存与执行状态。设备 ART 提供分配、类链接、GC 和线程暂停服务；增强库负责类演进需要的额外校验、迁移与一致性管理。

1. 用命名符号找到入口，用真实行为证明声明

公开 JVMTI 已经提供方法体重定义的基础。更深的结构演进则需要 ART 私有服务。项目通过命名 ELF 符号绑定这些服务，依据核对过的源码声明建立 ABI，并使用公开 JNI/JVMTI 观察做独立行为校准。

对库内部直接调用的重定义入口，项目采用 ShadowHook 安装 Inline Hook；只有确认调用点经过导入表时，PLT Hook 才适用。函数地址与对象字段偏移不从反汇编推算。Android 版本、设备型号或某个符号存在，都不能单独授予演进权限；当前通用适配以真实符号与行为证明选择能力，Build ID 用于记录证据来源。

这让适配围绕“设备实际上能提供什么”展开。通用算法放在 common 层，ARM64 和不同 ART 声明族保留各自的差异，避免每个版本复制一套引擎。

2. 以整批最终 DEX 为准

入口保留用户 Agent 原始的 jvmtiEnv*，继续检查调用者的重定义能力、参数和目标类。转换回调可能把原本只改方法体的补丁变成结构补丁，因此结构判断应围绕回调之后的最终 DEX，在 ART 事务内部完成。

相互依赖的类共享批次协调与进程级事务锁。在已覆盖的可恢复失败路径中，冲突或安全条件不满足时，整批返回错误，旧定义仍然有效。事务一旦进入不可失败的提交阶段，就不能再把内部异常包装成一个普通的“安全拒绝”。

3. 字段迁移与旧引用必须共同成立

结构变化会改变类元数据及字段布局。项目为兼容字段建立映射，延续已有值；新增字段使用默认值。类型或 static / 实例形态改变时，旧成员退役，新成员按新定义建立。处理父类变化时，还需要同步验证对象的继承字段来源和接收者类型关系。

运行时还有许多通往旧成员的路径：字节码解析缓存、反射对象、JNI ID、MethodHandle、VarHandle，以及编译代码中的快速访问。只更新新查询结果远远不够。增强库同时协调这些已覆盖的路径，阻止已退役成员或失效接收者继续被当作有效目标。

访问权限也有自己的语义。已经合法创建的句柄所持有的访问授权，不一定因后续可见性收窄而失效；final 写入约束、原生 JNI 写入语义与接收者有效性则需要分别处理。项目用具体调用路径的回归来证明这些边界。

4. 对正在执行的机器码，先证明能恢复

ART 同时存在解释执行、JIT 与 AOT。机器码可能把旧字段位置固化，或者把一个旧方法内联进调用者。重定义时，下一次查询的结果正确，还不足以保证暂停中的机器码能安全继续。

项目利用设备栈遍历、CodeInfo 和 StackMap 读取实际执行位置，并检查外层和内联层的寄存器恢复信息。信息足够、路径已校准时，协调去优化（Deoptimization），使执行回到安全路径；信息不足时，在旧定义完整的边界上拒绝，等待活动帧退出后重试。

05 / ENGINEERING DIRECTION

沿着同一条一致性路线继续推进

项目已经建立了标准入口、结构演进、状态延续、旧引用守卫和活动帧处理的验证基础。下一阶段把这些能力连接到更广的 ART 构建，并收紧每一场变化的生命周期。

以下为后续设计与验收方向。它们表达引擎的发展路线，区别于上文已有的设备能力证据。

统一事务所有权

通用 RunState 聚合同一次原始 ART 事务的线程状态、GC 排除、移动对象根、层级证明与 DEX 发布账本。先在普通可分配阶段准备完整根与存储，再进入连续安全窗口，刷新 GC 后的引用，最后完成发布、清理和提交。原始事务仍拥有最终边界；临时类与缓存必须在有效生命周期内提交或退款。

这条路线已经有组件和组合测试，完整正向发布及失败退款仍需实际生产链与设备证明。Android 11/12 的线程转换条件也要独立解决，不能借其他版本的窗口假设放行。

跨版本复用算法，逐项证明 ABI

Android 11–17 共用元数据、缓存和事务算法，只为真实变化的源码声明、缓存协议与线程服务建立差异层。每次启用能力，都核对实际设备符号、独立对象身份和行为校准，再通过冻结 APK 回归。通过公开能力、删除子集或物理帧读取，是各自的里程碑；完整结构演进有独立完成条件。

更精确的帧恢复与长期资源管理

扩展真实内联、并发和 AOT/JIT 混合调用的恢复矩阵，缩小解释执行回退范围；继续覆盖旧引用保活、元数据回收、ClassLoader 卸载和长时间前台交互。对缺少恢复信息的编译产物，先明确可恢复条件，再决定编译策略或去优化路径。

工程目标很具体：每一批类变更，都能解释清楚对象状态如何延续、旧引用如何处理、活动调用如何继续，以及失败时为何仍保留完整旧定义。
